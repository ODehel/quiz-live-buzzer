## Leçons de méthode
- **Le « silence » du spec entre CA-5 et CA-6 n'en est pas un** : « un renouvellement par message » et « l'`auth_success` de réponse ne change rien » donnent, ensemble, un compteur (rafale) et non un drapeau. Pas de remontée à Olivier (comportement observable déterminé par la conjonction des deux CA), mais consigné dans la décision #77 « à relire ». La borne de ce raisonnement : le comportement à l'ouverture d'une connexion avec une réponse jamais reçue (remise à 0 à l'ouverture) vient de CA-6 (« seul l'`auth_success` suivant une ouverture s'affiche »), pas d'une hypothèse sur le hub.
- **Rouge de compilation d'abord pour un changement d'interface** : `EXPECT_FALSE(sender.SendAuthRefresh())` ne compile pas tant que la méthode retourne `void` ; le passage à `bool` (retour toujours vrai) a donné les trois rouges de comportement, puis le vert.
- **Des tests de bout en bout avec le vrai `TokenSessionMessageSender`** (`ConnectionEventHandlerRenewalSessionTest`, écrivain et `TokenFetcher` stricts) complètent les tests au mock du gestionnaire : le mock ne dit pas ce que fait l'émetteur d'un login refusé, le vrai oui (`LoginRefusalListener` strict : aucun arrêt).
- **Une ancre de mutation doit être unique** : `token = fresh.token;` existe dans `SendAuth` et `SendAuthRefresh` ; le script vérifie le compte avant de muter.
- Environnement : même procédure qu'au handoff `1408`, sans `gtest_main` ; scripts de compilation (8 jobs, ~50 s les 28 suites) et de mutation hors dépôt dans `/tmp/fwbuild`. Pas de `session-close.ps1` (PowerShell absent) : handoff rédigé à la main d'après le gabarit.

## Points à challenger
- **Compteur remis à 0 à l'ouverture seulement** : un hub qui répondrait à `auth_refresh` par autre chose qu'un `auth_success` (ou jamais) rendrait muet le prochain `auth_success` de la même connexion. Sans importance tant que US-021 n'existe pas ; à revoir avec elle (consigné en dette).
- **`SendAuthRefresh` retourne un booléen** : interface publique modifiée pour que le gestionnaire sache si une réponse est attendue. Alternative écartée : un état « en attente » dans l'émetteur, interrogé par le gestionnaire.
- **Statut « Implémentée » dans l'index** alors que le bout en bout est impossible (US-021) : même logique que US-FW-003 (« Implémentée », messages du hub non émis), mais à relire : « Partielle » serait défendable tant que rien n'est constaté sur le matériel.
- **Le token du renouvellement devient le repli de `auth`** : non exigé par un CA, figé par un test.
- **Un `POST` bloquant par `token_expiring_soon`** dans le callback de réception (CA-5, coût déjà consigné) : non mesuré, non plafonné ; une rafale de N messages bloque `client.loop()` N fois la durée d'un login.
- **Mutant équivalent M19** : retirer le test du statut ne se voit pas ; si `LoginResult` change un jour (token non vide avec un statut d'échec), le test du statut redevient nécessaire.
- **Identité git** : le dépôt de la session est configuré `Claude <noreply@anthropic.com>`, pas l'identité d'Olivier de `docs/method/WORKFLOW.md` ; non modifié.
