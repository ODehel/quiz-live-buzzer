## Leçons de méthode
- Une question « remplace ou succède » (D4) se tranchait en lisant le contrat du hub **avant** la salve : US-019 CA-16 et CA-20 (aucun message pour une partie `PENDING`) rendent un message d'attente coûteux, et `auth_success` suffit. Les options chiffrées (0 ou 1 message hub) venaient de cette lecture, pas de la maquette.
- Un nom d'écran (« Connecté ») était cité dans sept US. Règle tenue : corriger d'une phrase **les seules** US dont un CA est contredit (010, 015, 007) et dire dans le `README` et la décision que les autres mentions se lisent « D4 », plutôt que réécrire sept fichiers.
- Le porteur naturel d'une information (le nom du participant dans `game_started`) peut être écarté parce qu'un second message (`game_resumed`) ne la porte pas : la dépendance entre deux messages se lit dans le contrat du hub, pas dans le code du firmware.
- Un chemin d'entrée ignoré du contrat (`PUT` ou `PATCH` du statut vers `OPEN`, US-010 CA-23, CA-36) n'est apparu qu'en cherchant **tous** les chemins vers le déclencheur : à faire pour tout message lié à une transition d'état du hub.
- Le plan des CA a été dressé avant la Porte 1 et chaque chiffre (couche et statut compris) recompté sur le tableau après écriture : aucun écart cette fois.
