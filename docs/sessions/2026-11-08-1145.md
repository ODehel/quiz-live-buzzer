## Leçons de méthode
- **Une cible proposée sans avoir lu le code peut être intestable** : la cible initiale (`refactor(rendering): share one display state…`) a été écartée à la lecture : `DisplayState` est sans état (méthodes `const`, aucun champ), donc une instance partagée ou deux ne se distinguent par aucun test ni mutation. Un refactor de structure doit pouvoir être contredit par un test ; sinon il attend le rouge qui le réclame (ici : la feature « effets d'écran »). À la porte 1, lire les fichiers concernés **avant** de proposer, pas après.
- **Une mutation survivante révèle une garde non couverte, même sans changement de comportement** : `advance != notFound` n'avait aucun test depuis `feat(rendering): show œ and typographic symbols…` ; le refactor l'a fait remonter. Un test né vert (spec) se prouve par la mutation qu'il tue.
- **Le banc natif se reconstruit en quelques minutes** (googletest et gmock `v1.15.2`, ArduinoJson `v7.4.3`, chaque suite compilée avec `-Werror=switch`, `-I` sur chaque `lib/*/`, `test/`, `test/fixtures`, `test/mocks`, et les sources `lib/*/*.cpp`). Un script de lancement (compilation de chaque suite, comptage via la ligne `[==========] N tests from`) vit hors dépôt, dans le répertoire de travail de session : le refaire à la prochaine session.
- **Une estimation de Flash reste une estimation, deuxième fois** : annoncé ~1,4 Ko (mesure x86 `-Os`), mesuré −876 octets sur l'`esp32` (environ 60 % de l'estimation). La RAM n'a pas bougé : l'économie des 5 nœuds de tas n'apparaît pas dans ce compteur (allocation à l'exécution), donc non mesurée. Citer le chiffre mesuré, jamais l'estimation, dans les handoffs.
- **Un smoke test d'un refactor doit dire ce qu'il prouve** : ici, le build `esp32` (Flash) et un rendu de « œ ». Il ne prouve pas les quatre autres glyphes ; ne pas le présenter comme couvrant tout.
