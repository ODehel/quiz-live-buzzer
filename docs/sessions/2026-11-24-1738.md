## Leçons de méthode
- Un écran de plus n'exige pas de port : `InitScreenDisplay` est un `LoginOutcomeDisplay` qui s'affiche sans condition ; la fixture de test passe par un `MockScreen` avec des littéraux (pas par le présenteur) pour ne pas écrire un test tautologique.
- CA-2 (« ne change plus ») se prouve par absence : aucun test neuf ne le porte seul, il est tenu par des tests existants cités dans US-FW-010. Le dire dans la spec plutôt qu'écrire un test factice.
- Le contrôle de syntaxe de `main.cpp` demande un noyau Arduino factice un peu plus riche pour `WebSockets` (`-DESP32`, `WiFiClientSecure.h`, `ESP_ARDUINO_VERSION_VAL`) que pour les seuls adaptateurs ; comparer la liste triée des erreurs avant et après reste la bonne preuve.
- Les suites natives se compilent à la main avec un petit script (inclusions `lib/*`, `lib/*/*.cpp`, `-lgmock_main`) ; 27 répertoires en environ une minute.

## Points à challenger
- **L'ordre dans `setup()`** (`lcd.init()`, `fillScreen`, `initScreenDisplay.Show()`, `WiFi.begin`) n'est prouvé par aucun test : un déplacement de la ligne passerait la CI. Seul le smoke test le voit.
- **Texte en un seul `TextScreen` à retours à la ligne** : la taille unique des trois lignes dépend de `GfxScreen` (CA-7), jamais constatée sur trois lignes sous le bandeau.
- **`InitScreenDisplay` et `LoginOutcomeDisplay`** sont deux classes minces voisines ; les fondre en un « affichage de démarrage » est possible, écarté (deux raisons de changer).
- **Pas de `RetainingScreen`** pour l'init (décision #69) : à revoir si une coupure pouvait un jour survenir avant le premier `auth_success`.
- **Le bandeau du `401` n'a pas bougé** (`Hidden()`) alors que `TopBarForInit()` existe : l'écart avec US-FW-015 CA-9 reste ouvert, volontairement hors périmètre.
- Le smoke test (écrit par un agent distinct, qui n'a vu ni le diff ni le code) a été lancé par Olivier sur le matériel : voir « Smoke test du 2026-11-24 ». Le script n'est pas dans le dépôt.
