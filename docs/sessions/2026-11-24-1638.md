## Leçons de méthode
- Le comportement de `loop()` (« rien quand le démarrage est arrêté ») ne se prouve que si les lecteurs d'appui sont derrière le même objet que dans `main.cpp` : la fixture câble `StartupSequence` et `BuzzerLoop` avec les mêmes lecteurs, et `Times(0)` sur `DeduceButton` fait la preuve.
- Un port par dépendance non testable (`ConnectionOpener`, `TokenUpdater`, `NetworkLoop`) coûte une classe de base et un `override` sur l'existant : aucun test existant n'a changé.
- Un contrôle de syntaxe de `main.cpp` contre les en-têtes réels est possible hors la classe `LGFX` ; comparer les erreurs avant et après le changement (même ensemble) vaut mieux qu'un « il compile ».
- Le nombre de tests annoncé par un handoff peut dériver (655 annoncés, 658 comptés ; cause non établie, probablement les 3 tests du second commit de la PR #123) : le réel est recompté à l'ouverture.

## Points à challenger
- **Les messages série après l'ouverture** : « Login OK… » est écrit après `Open()` et non avant. Défendu par la lecture de `WebSocketsClient::begin` (aucune écriture, aucune connexion), jamais constaté sur le matériel.
- **Deux états d'arrêt** (`StartupSequence::IsHalted()` et `NetworkHalt`), lus ensemble par `BuzzerLoop` : les fondre dans `NetworkHalt` ferait fermer un client jamais ouvert (écarté, voir #68).
- **`StartupSequence` dépend de classes concrètes** (`TokenAcquisition`, `LoginOutcomeDisplay`), pas d'interfaces.
- **`CA-11` : « `loop()` ne tourne pas pendant `setup()` »** reste un fait du framework Arduino ; le test prouve seulement que `Run()` ne lit ni appui ni réseau.
- Le câblage de `main.cpp` et l'adaptateur `WebSocketConnectionOpener` n'ont aucun test : un mauvais objet passé à `BuzzerLoop` (par exemple un autre `NetworkHalt`) ne se verrait qu'au smoke test.
- Aucun smoke test n'a été écrit ni lancé dans cette session.
