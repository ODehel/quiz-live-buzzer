- **Couche** : logique
- **Statut** : **Implémentée depuis le 2026-11-25** (`feat(token): log in without blocking the receive loop`, décision #80) : CA-2, CA-3, CA-5, CA-8 et CA-9, restés en écart de code depuis le cadrage, sont implémentés et testés en natif ; CA-6 inchangé (comportement et assertions : seul l'arrangement des tests a suivi l'interface, voir « Écart de preuve ») ; l'adaptateur `src/TaskAsyncLogin.cpp` et le câblage de `main.cpp` ne sont ni testés ni compilés pour l'`esp32`. **Chemin mort de bout en bout** inchangé (US-021 du hub). Avant ce cadrage : Implémentée, CA-1 à CA-7 rédigés depuis le réel le 2026-11-22, tous implémentés et testés en natif (CA-2, CA-3, CA-4 et CA-6 livrés par `feat(token): renew the session with a fresh token when the hub announces its expiry`, 2026-11-25 ; CA-5 et CA-7 testés par la même session). **Chemin mort de bout en bout** : le hub n'émet pas encore `token_expiring_soon` ni `token_expired` et ne traite pas `auth_refresh` (US-021), rien n'est constaté sur le matériel ni avec `scripts/fake-hub.ps1`
- **Dépend du hub** : US-021 (non implémentée au 2026-11-22, `quiz-live-server` à `ef57459`)

## User story

> **En tant que** joueur,
> **quand** la partie dure plus longtemps que la validité du token de mon buzzer,
> **alors** il le renouvelle de lui-même sans couper la connexion, et je ne vois rien changer à l'écran.

## Périmètre

Du premier `auth_success` à la fin de vie du token, sur une connexion ouverte :

1. le hub prévient le buzzer 300 s avant l'expiration (`token_expiring_soon`, US-021 CA-1 à CA-4) ; le buzzer n'a **aucun timer local** et ne lit pas `expires_in` : il obéit au hub (CDC §8.1) ;
2. à ce message, le buzzer redemande un token par un login frais (`POST /api/v1/token`) et l'envoie dans `auth_refresh` ; ce login ne bloque pas la réception et dure 5 s au plus, de l'envoi du `POST` à la fin de lecture de la réponse ; un seul login (d'ouverture ou de renouvellement) est en vol à la fois ; le hub répond `auth_success` (US-021 CA-10, CA-11) ;
3. sans renouvellement, le hub envoie `token_expired` puis ferme la connexion (`4002`, US-021 CA-6, CA-7) ;
4. aucun de ces messages n'arme ni ne désarme un mode, et le renouvellement ne se voit pas à l'écran.

**Hors périmètre** :

- le token frais redemandé à chaque connexion, reconnexions comprises (`auth`) : US-FW-005 CA-9 (décision #48 inchangée), dont le login d'ouverture est lui aussi non bloquant (décision #78) ; le login de `setup()` et le `GET` de la photo (US-FW-020, décision #63) restent bloquants, dette « Login du token : ce que le non-blocage ne couvre pas » ;
- la fermeture `4002`, son comptage et la reconnexion : US-FW-006 CA-5, CA-6 ; l'arrêt sur `401` à la reconnexion : US-FW-006 CA-11 ;
- le silence de l'Éliminé (aucun `auth_refresh`, aucun login) : US-FW-006 CA-9, CA-10 ;
- le format JSON de `auth_refresh` : US-FW-004 CA-9 ; le rendu d'`auth_success` à la reconnexion (« Connecté », bandeau) : US-FW-010 ;
- l'émission de `token_expiring_soon`, de `token_expired` et le traitement d'`auth_refresh` : US-021 du hub.

## Critères d'acceptance

Tous les CA sont de la couche **logique**. « Preuve » dit ce qui établit le CA (`constat` : lecture du code ; sinon les tests natifs, nommés ; les mutations de ceux nés verts) ; « Statut » dit où il en est dans le code au 2026-11-25 (libellés des CA-1, CA-4, CA-6 et CA-7 inchangés depuis le 2026-11-22 ; CA-2, CA-3 et CA-5 réécrits ou complétés, CA-8 et CA-9 ajoutés le 2026-11-25, tous précisés par la décision #79 ; le code a suivi le même jour, décision #80). Les tests ne portent pas de numéro de CA : la correspondance se fait par le nom des tests. Aucun smoke test n'est écrit dans cette session.

## Constats reportés

Rien de ce qui suit n'est un CA : ce sont des constats consignés dans `DEBTS.md`, à rouvrir comme indiqué.

- **Hub sans US-021** : au 2026-11-22 (`quiz-live-server` à `ef57459`), `ws-route.ts` ne traite pour un client authentifié que `request_game_state` ; aucun timer, aucun `token_expiring_soon` ni `token_expired`, `auth_refresh` ignoré. CA-1 à CA-7 ne se vérifient pas de bout en bout avant US-021 ; `scripts/fake-hub.ps1` n'émet pas non plus ces messages (non vérifié).
- **`POST` du renouvellement, non bloquant depuis le 2026-11-25** (décisions #78, #79 et #80) : CA-2 (non bloquant, 5 s), CA-5 et CA-8 (un seul login à la fois), CA-9 (résultat après fermeture) sont dans le code. **Ce qui suit décrit l'ancien état, avant la session de code** : le login se fait encore dans le callback de réception (`client.loop()` ne tourne pas pendant ce temps), `ArduinoHttpPoster` ne fixe aucun délai (non vérifié), et chaque message d'une rafale en déclenche un. Le hub coupe après 3 pings sans pong, un ping toutes les 30 s (US-015 CA-4, CA-7) : le risque, non mesuré, est ce que le non-blocage supprime ; ce qui reste est la dette « Login du token : ce que le non-blocage ne couvre pas ».
- **Points ouverts du cadrage du 2026-11-25** : tous tranchés par la décision #79 (CA-2, CA-3 : les 5 s ; CA-6 : justification du compteur ; CA-8 : `token_expiring_soon` pendant le login d'ouverture ; CA-9 : nouvelle connexion, `401` tardif, élimination). Rien ne reste ouvert ici ; le code a suivi le 2026-11-25 (décision #80).
- **Coupure faute de renouvellement** (CA-3, CA-4) : le message `token_expired` puis la reconnexion perdent le message de jeu d'un mode armé, `game_resumed` ne ré-armant rien (décision #49, constat « Mode armé pendant la coupure »).
- **Durée du token côté hub** : 3600 s par défaut, réglable (`JWT_EXPIRATION`) ; en dessous de 300 s, le hub prévient dès l'`auth_success`. Aucun CA : le comportement du buzzer est le même (CA-5, CA-8).
- **Écart de preuve** : CA-1 à CA-9 sont tenus par des tests natifs depuis le 2026-11-25 (décision #80). **CA-6 : comportement et assertions inchangés, mais l'arrangement de ses tests a dû suivre l'interface** : `SendAuthRefresh()` ne rend plus un booléen (le login est asynchrone), c'est `PollLogin()` qui dit si un `auth_refresh` est parti ; dans les sept tests de CA-6 du gestionnaire, `ON_CALL(…SendAuthRefresh()).WillByDefault(Return(true))` est devenu `ON_CALL(…PollLogin())…` et un `handler.PollSession()` suit chaque `token_expiring_soon` (les noms et les assertions n'ont pas bougé ; `…OfABurstIs…` garde son nom : l'arrangement est maintenant « un login se termine, puis un nouveau message arrive », comme le dit CA-6). Le fixture de ces tests passe d'une session simulée stricte à une session simulée tolérante (`NiceMock`), les nouveaux appels (`OnConnectionClosed`, `Abandon`, `PollLogin`) n'étant pas l'objet de ces tests. Restent non prouvés : l'appel HTTP de `ArduinoHttpPoster` (la correspondance statut → `LoginResult` de `HttpTokenFetcher` est testée, US-FW-005 CA-8) ; la tâche de `src/TaskAsyncLogin.cpp` et le câblage de `main.cpp` (jamais compilés pour l'`esp32`, jamais constatés sur le matériel ; voir US-FW-005, « Écart de preuve, login d'ouverture non bloquant ») ; l'enchaînement bout en bout avec un hub qui émet `token_expiring_soon` et répond `auth_success` (US-021, non implémentée : aucun smoke test dans cette session, `scripts/fake-hub.ps1` n'émet pas ces messages).
