- **Dépend du hub** : US-003, US-009

## User story

> **En tant que** joueur,
> **quand** je mets mon buzzer sous tension,
> **alors** il rejoint le réseau, obtient un token auprès du hub, s'authentifie sur le WebSocket et n'entre en jeu qu'une fois le hub d'accord, sans jamais réagir à un appui avant ce moment.

## Périmètre

Séquence d'initialisation linéaire, de la mise sous tension à `auth_success` :

1. connexion au Wi-Fi ;
2. `POST /api/v1/token` avec les identifiants du buzzer, réessayé tant qu'il échoue ;
3. ouverture du WebSocket `ws://<ip>:<port>/ws` ;
4. à l'ouverture, un second login (token frais), puis `auth` avec ce token ; ce login ne bloque pas la réception et dure 5 s au plus, de l'envoi du `POST` à la fin de lecture de la réponse (CA-8, CA-9, CA-12) ;
5. `auth_success` met fin à l'init.

Le login de l'étape 2 (dans `setup()`) reste bloquant : init statique, décision #53. Un `401` au login arrête le buzzer jusqu'au redémarrage. Tout autre échec est réessayé sans fin. Pendant l'init, un appui est sans effet. Le compteur d'élimination est inactif pendant toute cette phase.

**Hors périmètre** :

- ce que le joueur voit pendant l'init (logo, bandeau clignotant, écran « Connecté ») : US-FW-010 ; l'écran « Connexion refusée » : US-FW-015 (ici, seul le fait qu'il est affiché compte, CA-5) ;
- le format JSON de `auth` : US-FW-004 CA-9 ; `auth_refresh`, `token_expiring_soon` et `token_expired` : US-FW-007 ;
- la perte de connexion après `auth_success`, la reconnexion, le compteur et l'élimination : US-FW-006 ; seul le moment où le compteur est armé est ici (CA-10) ;
- le comportement des modes armés : US-FW-002 et US-FW-003 ; le CA-11 ne reprend de US-FW-002 CA-8 que l'effet pendant l'init ;
- la configuration du Wi-Fi, des identifiants et de l'adresse du hub par NFC ou QR code : US-FW-022 ;
- le login du renouvellement (non bloquant, un seul à la fois) : US-FW-007 CA-2, CA-5, CA-8, CA-9 ; le téléchargement de la photo (`GET`, US-FW-020, décision #63), dont le blocage reste en dette.

## Critères d'acceptance

Tous les CA sont de la couche **logique**. « Preuve » dit ce qui établit le CA (`constat` : lecture du code, sans test natif, car la séquence vit dans `src/main.cpp` ou dans un adaptateur de `src/`) ; « Statut » dit où il en est dans le code au 2026-11-22 (CA-8, CA-9 et CA-12 : cadrage du 2026-11-25, complété par la décision #79, code du 2026-11-25, décision #80). Les tests ne portent pas de numéro de CA : la correspondance se fait par le nom des tests. Aucun smoke test n'est écrit dans cette session.

## Constats reportés

Rien de ce qui suit n'est un CA : ce sont des constats consignés dans `DEBTS.md`, à rouvrir comme indiqué.

- **Deux logins au démarrage** (décision #48) : CA-9 décrit le comportement tel quel ; le second login est non bloquant depuis le 2026-11-25 (décisions #78 et #80). Le « ne redemander que près de l'expiration (`expires_in`) » reste une piste de la dette « Login du token : ce que le non-blocage ne couvre pas », non traitée (décision #78).
- **Appui pendant le login d'une reconnexion, avant `auth`** (décision #78) : dans un mode armé, même règle que la coupure, constat « Mode armé pendant la coupure » (US-FW-006, décision #49) : ni CA ni code, dette conservée. Au premier démarrage, l'Inerte ignore l'appui (CA-11) : rien à changer.
- **Points ouverts du cadrage du 2026-11-25** : tous tranchés par la décision #79 (CA-8 : les 5 s ; CA-9 et CA-12 : nouvelle connexion, `401` tardif, élimination, `token_expiring_soon` pendant le login d'ouverture ; US-FW-007 CA-6, CA-8, CA-9). Rien ne reste ouvert ici ; le code a suivi le 2026-11-25 (décision #80).
- **Écart de preuve, login d'ouverture non bloquant** (décision #80) : la logique est prouvée en natif avec un faux login et une fausse horloge (`FakeAsyncLogin`, `FakeClock`) ; **non prouvé** : la tâche FreeRTOS de `src/TaskAsyncLogin.cpp` (jamais compilée pour l'`esp32`, syntaxe contrôlée contre des stubs et comportement exercé hors dépôt avec des threads, sous ASan et UBSan), le câblage de `main.cpp` (`SessionPollingNetworkLoop`, `TaskAsyncLogin`, `ArduinoClock`), la taille de pile de la tâche (8 192 octets, non mesurée), le fait que `client.loop()` tourne réellement pendant le `POST` (jamais constaté sur le matériel). Le `POST` d'un login abandonné n'est pas interrompu sur le réseau : il va au bout du délai du framework (non vérifié) et son résultat est jeté, donc deux `POST` peuvent être en vol côté hub pendant quelques secondes. Le délai d'authentification du hub (fermeture `4003`) n'est pas connu du firmware : un login d'ouverture qui dure jusqu'à 5 s retarde d'autant l'envoi d'`auth` (non constaté, à relire dans US-009 du hub).
- **`401` pendant une reconnexion** : tranché par US-FW-006 CA-11 (décision #49) et implémenté le 2026-11-23 : `auth` n'est pas envoyé, le buzzer s'arrête comme au démarrage. Un autre échec du login garde la règle de CA-9 (dernier token).
- **Message de jeu avant `auth_success`** : décision #47, rien de nouveau ici ; un appui avant `auth_success` est sans effet par l'Inerte (CA-11), pas par un état « authentifié ».
- **Séquence bloquante, init statique** : `setup()` garde la main pendant le Wi-Fi et le login (CA-1, CA-2, CA-4) ; ce login reste bloquant (décision #78, #53) ; l'écran d'init statique est dessiné avant (US-FW-010 CA-1, `feat(startup): show the init screen while the buzzer connects`, non constaté sur la dalle) ; le bandeau clignotant reste à US-FW-010 (constat reporté). Dette existante.
- **Adresse du hub en dur, HTTP clair** : `192.168.1.183:3000` figure deux fois dans `main.cpp`, les identifiants partent sans TLS. Dette existante, à rouvrir avec US-FW-022.
- **Écart de preuve** : cas d'échec de la lecture de la réponse (CA-7) et correspondance statut HTTP → `LoginResult` (CA-8) soldés le 2026-11-23 ; arrêt de `loop()` après `401` (CA-5) et absence de lecture d'appui pendant `setup()` (CA-11) soldés en natif le 2026-11-24 : la séquence d'après le Wi-Fi (`StartupSequence`) et le tour de `loop()` (`BuzzerLoop`) vivent dans `lib/startup/`, `main.cpp` ne fait plus que les câbler. Ne reste que ce câblage (compilé en syntaxe seulement, voir la dette « Démarrage : preuves manquantes ») et le constat sur la dalle du chemin `401` au démarrage. Les messages série (« Login OK… », « Login refused… ») sont écrits par `setup()` d'après le résultat de `Run()`, après l'ouverture du WebSocket et non avant : `begin()` n'écrit rien et ne connecte pas (la connexion se fait dans `loop()`), l'ordre observable sur le port série est inchangé.
- **Écart de preuve, CA-7** : la preuve est `LoginResponseDeserializer` seul, avec ArduinoJson 7.4.3. Le texte du CA ne fixe pas la forme exacte du « texte parasite » : le test retient `{"token":"abc"} stray text`. Le passage du texte lu à `LoginResult` et au réessai est prouvé par CA-8 (`HttpTokenFetcher` avec ce décodeur, puis `TokenAcquisition`). Non constaté : un hub réel qui renvoie un corps tronqué ou parasite (le hub envoie des corps complets).
- **Écart de preuve, CA-8** : la preuve est `HttpTokenFetcher` (`lib/startup/`) devant un faux `HttpPoster` : les statuts sont ceux du CA, jamais lus dans le code. Le CA dit « un `200` sans token : échec réessayé » ; au niveau de `HttpTokenFetcher` ce cas rend `Success` avec un token **vide** (comportement conservé, testé), et c'est `TokenAcquisition` qui le réessaie : les deux tests `Acquisition…` prouvent le CA de bout en bout. Non prouvé : l'appel `HTTPClient` de `ArduinoHttpPoster` (`src/`, vérifié par compilation de la syntaxe contre des stubs d'Arduino seulement, pas de build `esp32`) ; le code de transport réel que `HTTPClient::POST` rend pour un hub injoignable (les tests utilisent `-1` et `-11`, valeurs choisies parmi les négatifs, sans que le CA en fixe une) ; le délai du `POST` lui-même (la borne de 5 s du login en jeu est tenue par la logique, voir « Écart de preuve, login d'ouverture non bloquant ») ; un `401` réel du hub. `ArduinoHttpPoster` lit désormais le corps quel que soit le statut (avant : seulement pour `200`) : non constaté sur le matériel pour un statut d'erreur. Un test `Acquisition…` fait boucler sans fin `TokenAcquisition` si un mutant rend `401` en échec : le garde-fou est le délai d'exécution, comme dans `test_startup`.
- **Écart de preuve, CA-6** : la preuve est le corps produit par `SerializeLogin` (test natif) et le constat sur matériel du 2026-11-23, avec le hub local : le journal du hub montre un `POST /api/v1/token` `200` (« Authentication successful », `quiz_buzzer_01`) au premier essai, aucun `400`, puis l'ouverture du WebSocket, un second login `200` et `WEBSOCKET_AUTHENTICATED` ; le moniteur série affiche une fois « Login OK, opening the WebSocket. », sans nouvelle tentative. Non relevés : l'écran du buzzer, l'effet d'un appui avant et après `auth_success`, et le contraste avec l'ancien code (non rejoué sur `main`). Le moniteur série ne journalise pas `auth_success` : c'est le journal du hub qui l'établit.
